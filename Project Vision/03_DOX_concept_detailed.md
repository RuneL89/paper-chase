# LLM Wiki CLI — DOX Concept (Detailed)

This document explains how the LLM Wiki CLI uses the **DOX Framework** as inspiration for organizing the wiki. It is written for anyone joining the project without prior context, so they understand the philosophy, the contract hierarchy, and the difference between the DOX original and this project's adaptation.

---

## 1. What is the DOX Framework?

The DOX Framework is a system for organizing documentation in a cascading, hierarchical way. Its central idea is that a large knowledge base should be broken into smaller, self-contained units, each governed by a binding contract that explains what belongs there and how to navigate it.

The canonical DOX reference is:

> https://github.com/agent0ai/dox/blob/main/AGENTS.md

In the original DOX design, the top-level document is `AGENTS.md`. It acts as the constitution of the knowledge base: it defines the folder structure, page types, naming conventions, tag taxonomy, and rules for the entire system. Sub-folders may have their own more specific contracts, creating a cascade of documentation from the general to the specific.

The key insights from DOX are:

- **Cascading contracts:** The contract at the top level governs the whole; contracts at lower levels govern their own sub-trees.
- **Self-describing folders:** Every folder has a contract that explains what it contains, so a reader can navigate without guessing.
- **Binding rules:** The contract is not just advice; it is the specification that the system (and any AI agent) follows.
- **Separation of structure from content:** The contract defines the structure; the pages are the content.

This project adapts these ideas, but changes the mechanism: the contracts are written in `index.md` files, not `AGENTS.md`.

---

## 2. Why `index.md` Instead of `AGENTS.md`?

In the original DOX Framework, `AGENTS.md` is both the human-readable contract and the machine-readable specification. In the LLM Wiki CLI, these two roles are split:

| Role | File | Audience | Purpose |
|---|---|---|---|
| **Contract** | `index.md` hierarchy | Humans and research agents | Navigate the wiki; understand what each folder contains and how pages are linked. |
| **Ingestion guide** | `AGENTS.md` | The LLM Extractor | Tell the LLM how to organize and write this specific wiki. |

The reason for this split is practical. The wiki is generated by the LLM, and the generated structure is dynamic: it depends on what the corpus actually contains. The `index.md` files must reflect the actual structure on disk. The `AGENTS.md` tells the LLM what rules to follow when creating that structure.

The `index.md` files are generated by the **DOX Writer** — an LLM-driven component that runs after all chunks have been ingested (see §6). They are not written during chunk processing. This separation ensures that the navigation contracts are always consistent with the actual content.

## 3. The Folder Hierarchy

### 3.1 Top-Level Folders

Every wiki has these top-level folders:

```
wikis/<slug>/
  raw/                    -- Source PDFs (immutable)
  documents/              -- Raw extracted chunks from PDFs
  sources/                -- Provenance records for each PDF
  entities/               -- Named real-world things
    <sub-folders>/        -- Created dynamically by the LLM
  topics/                 -- Themes and concepts
    <sub-folders>/        -- Created dynamically by the LLM
  index.md                -- Wiki-level navigation contract
  AGENTS.md               -- Ingestion instructions for the LLM
  .state/                 -- Internal state (hashes, extractions, rolling memory)
```

### 3.2 Dynamic Sub-Folders

The LLM creates sub-folders under `entities/` and `topics/` as needed. Examples:

```
entities/
  people/
    executives/
    politicians/
    auditors/
  companies/
    offshore/
    public/
    private/
  organizations/
    ngos/
    government-bodies/

topics/
  financial/
    revenue-recognition/
    tax-structures/
  legal/
    regulatory-investigations/
    litigation/
  regulatory/
    compliance/
    filings/
```

The LLM decides the folder path for each entity based on `AGENTS.md` instructions and the current folder structure. The **first folder assignment wins**: once an entity page exists in a folder, it stays there. Later chunks add evidence to the existing page.

### 3.3 Folder Naming Rules

- Use lowercase with hyphens (kebab-case).
- No spaces, no special characters.
- Names are written in the wiki's **output language** and transliterated to ASCII kebab-case when they contain non-ASCII characters (`04_orchestration_detailed.md` §9).
- Maximum depth: 3 levels below `entities/` or `topics/` (e.g., `entities/people/executives/` is valid; `entities/people/executives/ceos/founders/` is not).
- The LLM may create new sub-folders, but never outside `entities/` or `topics/`.

## 4. The `index.md` Contract Hierarchy

### 4.1 Levels of Index

| Level | File | Purpose | Generated By |
|---|---|---|---|
| Workspace | `wikis/index-of-indexes.md` | Lists all wikis in the workspace. | DOX Writer |
| Wiki | `wikis/<slug>/index.md` | Lists all folders and the wiki's scope. | DOX Writer |
| Folder | `wikis/<slug>/<folder>/index.md` | Lists pages in the folder and the folder's contract. | DOX Writer |
| Sub-folder | `wikis/<slug>/<folder>/<sub>/index.md` | Lists pages in the sub-folder. | DOX Writer |

### 4.2 What an `index.md` Contains

Every `index.md` must have:

```yaml
---
title: "Folder Name"
type: index
wiki: <slug>
updated: "2026-07-16T10:00:00Z"
children:
  - page-1.md
  - page-2.md
  - sub-folder/index.md
---
```

And a body that includes:
- **Title and scope** — what this folder or wiki is about, written as rich, human-readable prose.
- **Catalog** — a list of pages and sub-folders inside, with `[[page-name|Page Title]]` wikilinks (Obsidian-native target|display form) so the reader can navigate.
- **Navigation** — guidance on where to start and links to parent and sibling folders.
- **Statistics** — counts of pages, sources, and page types.

The prose is generated by the **DOX Writer**, an LLM that reads the actual pages in the folder, the wiki's `AGENTS.md`, and the rolling memory, so the description reflects the real content rather than the folder name alone.

The workspace-level `wikis/index-of-indexes.md` follows the same contract with two exceptions: it has **no `wiki` field** (it governs every wiki, not one), and its `children` are the per-wiki root indexes (`<slug>/index.md`, vault-relative inside `wikis/`). Its body sections are `## Wikis` (catalog of wiki root indexes) and `## Statistics` (wiki count plus corpus totals).


### 4.3 Example: Wiki-Level `index.md`

```markdown
---
title: "Acme Annual Reports"
type: index
wiki: acme-reports
updated: "2026-07-16T10:00:00Z"
children:
  - entities/index.md
  - topics/index.md
  - documents/index.md
  - sources/index.md
---

# Acme Annual Reports

This wiki contains 25 years of Acme Corp financial filings, organized into entities, topics, documents, and sources. The documents were extracted from annual and quarterly reports; the entity and topic pages were assembled by the Materializer from the Extractor's structured output.

## Start Here

- [[entities/people/executives/index|Executives]] — Key people across all reports
- [[revenue-recognition|Revenue Recognition]] — How Acme reports revenue
- [[acme-bvi|Acme BVI]] — Offshore subsidiary

## Statistics

- Sources: 25
- Document pages: 125
- Entity pages: 47
- Topic pages: 12
```

### 4.4 Example: Folder-Level `index.md`

```markdown
---
title: "Executives"
type: index
wiki: acme-reports
updated: "2026-07-16T10:00:00Z"
children:
  - john-smith.md
  - jane-doe.md
---

# Executives

This folder contains people who hold executive positions (CEO, CFO, board members) in companies mentioned in the corpus. The pages list every mention, relationship, and claim extracted from the source documents, with citations back to the original PDF pages.

## Pages

- [[john-smith|John Smith]] — CEO of Acme Corp
- [[jane-doe|Jane Doe]] — CFO of Acme Corp

## Navigation

- Parent: [[entities/people/index|People]]
- Sibling: [[entities/people/politicians/index|Politicians]]

## Statistics

- Pages: 2
- Sub-folders: 0
- Sources: 0
```

## 5. Structural Change Logging

When the LLM creates a new folder or reorganizes the taxonomy, the change is logged in `.state/proposals/structural-changes.json`:

```json
{
  "changes": [
    {
      "timestamp": "2026-07-16T10:00:00Z",
      "type": "new-folder",
      "path": "entities/companies/offshore",
      "reason": "47 offshore entities identified in Panama Papers chunk 12",
      "affectedEntities": ["acme-bvi", "shell-corp-ltd"]
    }
  ]
}
```

The human can review this log after ingestion. If they disagree with a change, they can revert it via version control or edit `AGENTS.md` and re-run `ingest`.

## 6. The DOX Writer

The DOX Writer is an **LLM-driven component** that runs after all wiki pages have been completely written. It turns the raw folder structure into rich, navigable `index.md` contracts.

**When it runs:**

The DOX Writer is the final step in the ingest pipeline, placed **after materialization, optional synthesis, and validation** of the content pages:

```
Extract PDFs → Extractor → Materializer → Synthesis Writer → Validate content pages → DOX Writer → Re-validate wiki
```

No DOX contract can be written until the wiki pages exist, because the DOX Writer reads the actual page contents to understand what each folder contains.

**What it does:**

1. Scans the entire wiki tree (excluding `raw/` and `.state/`).
2. Builds a tree of folders and content pages.
3. For each folder that contains `.md` files or sub-folders, and for the wiki root:
   - Extracts the accurate structure: children list, sub-folder list, page titles, and statistics.
   - Reads the full content of the pages in that folder.
   - Passes the pages, the wiki `AGENTS.md`, and the rolling memory to the LLM.
   - Asks the LLM to write a rich `index.md` with: title, description, catalog, navigation, and statistics.
   - Writes the LLM-generated markdown to `index.md` inside the folder.
4. Runs a final validation pass over the wiki, including the new DOX pages, so any broken links or schema issues are caught.

**The workspace pass:**

After the per-wiki contracts are written, the DOX Writer runs one final workspace-level pass at the end of every ingest. The workspace index is **the topmost parent in the same bottom-up chain** — folder indexes are written deepest-first, then the wiki root index, then the workspace index — and it follows the same rule as every other parent: **it synthesizes only the freshly-written `index.md` contracts of its direct children (the wiki root indexes) and never re-reads the content pages inside the child wikis.**

1. Lists every wiki in `wikis/` that has a root `index.md`.
2. Reads each wiki's freshly-written root `index.md` (the same bottom-up summary-of-summaries pattern used for folder parents — these are the pass's only content input).
3. Calls the LLM once to write a rich `wikis/index-of-indexes.md` describing what each wiki holds and how the workspace is organized.
4. Deterministic code supplies and re-imposes the exact children list (`<slug>/index.md` per wiki) and the statistics (wiki count plus corpus totals); any LLM failure falls back to the deterministic contract, exactly as for per-folder indexes.

The workspace pass writes prose in the **output language of the wiki whose ingest triggered it** (`04_orchestration_detailed.md` §9). It sits inside `wikis/` so the whole `wikis/` folder can be opened as a single Obsidian vault where every link resolves. A wiki only appears once it has been ingested (init alone does not create a root `index.md`).

**What the LLM sees for each folder:**

- The folder path and the list of files and sub-folders it contains.
- The full markdown content of every page in that folder (not just titles).
- The wiki's `AGENTS.md` constitution, including its writing rules and style guidance.
- The rolling memory (`wikis/<slug>/.state/rolling-memory.json`).

**What the LLM writes:**

- A rich, human-readable description of the folder's scope, based on the actual pages inside it, following the writing rules in the wiki's `AGENTS.md` (plain language, journalist test, no invented facts, `[[page-name|Page Title]]` wikilinks, etc.).
- All prose is written in the wiki's **output language** (recorded in `AGENTS.md`, see `04_orchestration_detailed.md` §9); page titles and entity names stay verbatim regardless of language.
- A `## Pages` catalog with `[[page-name|Page Title]]` wikilinks (`[[folder/index|Folder Title]]` for sub-folders).
- A `## Navigation` section with links to parent and sibling folders.
- A `## Statistics` section with counts.

The exact children list and statistics are supplied by deterministic code so the LLM cannot hallucinate files or counts.

**What it does NOT do:**

- It does not create new folders.
- It does not move pages.
- It does not write content pages.
- It does not decide taxonomy; it describes the taxonomy that the Extractor and Materializer already produced.

The DOX Writer is the map written after the territory is settled.
