# wikis/ — DOX contract

## Purpose

Runtime workspace for generated wikis. `chase init <slug>` creates `wikis/<slug>/` here (or under a custom `-w` workspace); `ingest` fills it with document pages, source pages, and state.

## Ownership

* `<slug>/` — one generated wiki: `raw/` (source PDFs, never modified), `documents/` (raw extracted chunks), `sources/` (provenance pages), `entities/`, `topics/`, `.state/` (tooling state, e.g. `ingestion.json`, `language.json` — the Phase 7 per-wiki language record: `outputLanguage`, `lastInputLanguage`; Phase 14 adds `curation-report.json` — the per-run topic/entity curation outcome incl. fallbacks, vetoes, deletions, and rewritten links, with Phase 21 additive `fromSticky`/`decidedThisRun`/`proposedPairs`/`autoApplied`/`splitReversals` audit fields and Phase 22 additive `clusters`/`clusterDenials`/`proposedClusters` — and `curation-overrides.json` — the user-editable `{"neverMerge": [["slug-a","slug-b"]]}` veto list, created empty on first curation run; Phase 16 adds `synthesis-state.json` — the per-page synthesis completion memory `{ "pages": { "<wiki-rel path>": { "mode", "dataHash", "synthesizedAt" } } }` behind resume-skipping and Materializer byte-preservation; Phase 16 v1.0.4 adds `transport-stalls.jsonl` — the per-attempt 429/5xx stall audit log (timestamp, callType/context, provider, model, statusCode, attempt/maxAttempts, exhausted, waitSeconds, provider error message; written beside `llm-calls.json` so the call log's cost/count semantics stay untouched); Phase 26 adds `amendment-log.jsonl` — ONE JSON line per amendment EPISODE (timestamp, page, pdf, attempts, op-type counts, outcome `patched` | `fallback-full-synthesis`, cause, outputTokens; the cost evidence of the per-PDF patch-amendment path); Phase 21 adds `curation-decisions.json` — the STICKY identity-decision record, see Local Contracts), and a generated `AGENTS.md` constitution (from `templates/AGENTS.md`; binding for every LLM call in that wiki, managed by the CLI — never hand-edited; includes the wiki's `## Language` section since Phase 7). Phase 22: `entities/` also carries `type: composite` pages — one rich article pooling 2-4 logically-mapped entities of a ratified rollup class (member pages are never written; member names stay findable via the composite's `aliases`). Phase 23: the ratified top-level `comparisons/` folder carries `type: comparison` pages — ONE article per comparison-table SUBJECT (identity = the canonical subject-entity slug when resolvable, normalized-title slug only as fallback), each source's table preserved verbatim in its own dated `## Table: <source>, p. <page>` section (cross-PDF drift embraced, never force-merged), with the deterministic `## Related comparisons in prose` bridge linking out to the topic/entity pages where free-text comparisons live; no `comparisons/` artifacts appear in wikis whose corpora have no comparison tables
* `index-of-indexes.md` — the workspace-level DOX contract (Phase 6, 2026-07-20 amendment; per-wiki segments 2026-07-21): lists every wiki that has a root `index.md`; composed of a coherent cross-wiki prose block (marked `<!-- workspace-prose -->`, regenerated only when the wiki set changes) and per-wiki catalog lines (each written by that wiki's own ingest in its own output language and preserved byte-for-byte otherwise); re-composed by the DOX Writer's workspace pass at the end of every ingest; managed by the CLI — never hand-edited. Phase 24: gains a `## Cross-Wiki Discovery` section linking `cross-wiki/index.md` (before `## Statistics`) while cross-wiki artifacts exist — preserved byte-for-byte across re-compositions, omitted when no artifacts exist
* `cross-wiki/` — Phase 24 (vision `03` §3.1/§4.1 amended 2026-08-09): the workspace-level Cross-Wiki Discovery artifact set, written by the cross-wiki pass (`crossWiki` ingest option, CLI/TUI default-on) and created only when the workspace has ≥2 wikis: `index.md` (root contract), `entities.md` (the cross-wiki entity registry — every entity appearing in ≥2 wikis), `relationships.md` (the canonical-predicate cross-wiki relationship graph), `topics/<cluster-id>.md` + `topics/index.md` (semantic topic clusters). All pages are `cross-wiki-index`/`cross-wiki-topic` type, carry no `wiki` field, make no factual claims, and link to per-wiki pages with path-qualified wikilinks (`[[wiki-slug/folder/page|Title]]`). Derived and read-only — the pass NEVER edits per-wiki content pages; the folder is never a wiki (excluded from every wiki enumeration)

## Local Contracts

* This folder holds generated data, not source code; the repo only tracks the folder itself (`.gitkeep`) — wiki contents are user data
* Tests do not create or modify wikis here; they run against temp workspaces (see `tests/AGENTS.md`). Sole exception: Phase 2 gate tests READ the committed `test-wiki` fixtures (`documents/golden-master-part-001.md`, `AGENTS.md`) as extractor input — read-only, never written by tests
* Each wiki's `AGENTS.md` is that wiki's constitution (a generated artifact per `templates/AGENTS.md`), not a DOX contract for this repo; DOX contracts for generated wikis arrive with the DOX Writer in a later phase
* Opening `wikis/` as a single Obsidian vault is the supported way to navigate across wikis: `index-of-indexes.md` is the vault-root contract and its `[[<slug>/index|<Wiki Title>]]` links resolve by pure file lookup
* `.state/curation-decisions.json` (Phase 21) — the sticky curation record, shape `{ "decisions": [{ "concern": "topics"|"entities", "action": "merge"|"drop"|"cluster", "from": [slugs], "into": slug (absent for drops), "signal": "<signal-name>"|"model", "decidedAt": ISO, "runId": ISO }], "splits": [slug] }`. The tool appends every applied merge/drop and pre-applies the record deterministically before each curation pass, so decided identities are never re-litigated. **The `splits` escape hatch is the ONLY reversal** (merges are one-way by default): hand-edit `splits: ["slug"]` and the next materialize un-applies any recorded merge/cluster whose `into` or `from` contains the slug — both pages are rebuilt, the reversal is logged in `curation-report.json` `splitReversals`, and the pair returns to the candidates. The slug stays listed (the split holds, including against the deterministic auto-merge tier) until the pair is re-decided — a new applied decision touching the slug CONSUMES it (the tool removes it from `splits`). For a PERMANENT split, use `curation-overrides.json` `neverMerge` instead (it also beats sticky records, auto-apply, and confirms). The tool never otherwise edits `splits`; a malformed file is backed up to `curation-decisions.corrupt.json` and rebuilt
* `.state/curation-decisions.json` cluster records (Phase 22, the five-class rollup amendment) — an `action: "cluster"` record groups 2-4 entities into ONE composite page: `into` is the composite's slug (a member), `from` lists the OTHER members (the member set re-derives as `[into, ...from]`), and the additive `class` (1-5) + `rationale` carry the rollup metadata. Clusters are allowed ONLY within the five ratified classes: (1) abbreviation/name-variant, (2) brand↔generic substance, (3) indicator↔measured concept 1:1 (exactly one indicator slug + one concept slug), (4) facility↔city when the facility is the city's story, (5) same-name different-type (org↔location, the region name-forms). The composite page (`type: composite`, at the `into` member's folder/slug) carries the `class`, the `members` block (2-4 entries with slug/title/type), and every member title in its `aliases`; member pages are NOT written and member-targeted wikilinks resolve to the composite. A cluster is NOT a merge — identities stay in the graph; only the page is shared. A `splits` entry naming any member (or the `into`) DISSOLVES the cluster at the next materialize (member pages rebuilt, the composite page removed, the reversal logged); a `neverMerge` pair inside a cluster vetoes it the same way
