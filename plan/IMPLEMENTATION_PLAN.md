## 1. Executive Summary

This plan translates the canonical requirements in `Project Vision/` and `AGENTS.md` into a sequence of implementation sprints. The current codebase has the *scaffolding* of the LLM Wiki CLI (workspace discovery, PDF extraction, chunking, state management, basic writers, and orchestrator stubs) but is **not yet a true LLM-driven wiki compiler**. The biggest gaps are:

1. The **LLM is not the author of markdown content**. Document pages are assembled deterministically from extracted text; the ChunkWriter does not produce LLM-written synthesis, citations, or wikilinks.
2. The **sub-agents are regex/heuristic stubs**, not LLM agents.
3. There is **no `init` command** and **no per-wiki `AGENTS.md` ingestion guide** produced during `sample`.
4. **Structural change proposals** and human approval are not implemented.
5. **Sampling strategies** for different document categories are not implemented.
6. The **Critic** is a deterministic schema checker, not an LLM review agent.
7. **Completeness checks** that compare LLM-written pages back to extracted input are missing.

The plan below groups the work into six natural sprints. Each sprint is independently shippable and ends with both technical acceptance criteria (TAC) and user-acceptance criteria (UAT). Every requirement is tied back to the `Project Vision/` files and `AGENTS.md`.

## 2. Current State Analysis

The current codebase has 39 TypeScript files under `src/`. A quick audit against the vision reveals the following gaps.

### 2.1 Missing `init` Command

`Project Vision/01` §8.1 states:

> A new wiki is created with an `init <slug>` command. This command: creates the workspace directory structure; creates the wiki folder `wikis/<slug>/` with an empty `raw/` folder; writes an initial `AGENTS.md` ingestion guide tailored to the wiki's expected content; creates a skeleton wiki-level `index.md`.

`AGENTS.md` lists the commands as `sample, ingest, ingest-all, status, configure-llm, test-llm` — `init` is missing. Today the user must manually create the wiki folder before running `sample`.

### 2.2 `sample` is Document-Centric, Not Corpus-Centric

The vision says `sample` analyzes the *corpus* in `raw/` and chooses a sampling strategy:

> The sampling strategy must adapt to the nature of the documents in the corpus. The orchestrator chooses or is configured with a strategy appropriate to the document collection, such as: a collection of smaller, similar documents; a single very large document; a collection of similar but very large documents; a mixed corpus. (`Project Vision/01` §8.2)

Current `sample` takes a single `pdfPath` argument and processes that one PDF. It does not classify the corpus, select a strategy, or produce a corpus-level folder plan.

### 2.3 The LLM Does Not Write Markdown Content

`Project Vision/01` §3 Principle 1 is explicit:

> The LLM does all research, planning, and writing of markdown. This includes not only synthesized summaries, analyses, and connections, but also the faithful transcription of extracted text, tables, and figure descriptions into markdown. Local deterministic code handles PDF extraction, file I/O, hashing, schema validation, and orchestration, but it never drafts or mutates markdown bodies.

Current `src/writers/document.ts` writes a deterministic template containing chunk title, page range, and extracted text. The orchestrator's `chunkWriter` returns only `{ files: Record<fileName, title> }`. There is no LLM-driven synthesis, no key-claims section, and no inline `[^srcN]` citations generated by the LLM.

### 2.4 Sub-Agents Are Deterministic Stubs

`Project Vision/04` §4.4 describes the seven sub-agents as LLM-driven roles. Current implementations are:

- `StructureAnalyst`: derives headings and sections from existing extraction metadata, no LLM call.
- `EntityExtractor`: regex patterns for people, organizations, locations, etc.; no LLM call.
- `RelationshipExtractor`: finds co-occurring sentences between regex entities; no LLM call.
- `EvidenceCollector`: splits sentences heuristically; no LLM call.
- `PagePlanner`: calls the LLM but the prompt is shallow and does not pass the current `AGENTS.md` or rolling memory.
- `ChunkWriter`: returns file names and titles only; no LLM call.
- `Critic`: deterministic schema check; no LLM call.

### 2.5 No Per-Wiki `AGENTS.md` Ingestion Guide

`Project Vision/02` §7 says:

> `AGENTS.md` is the **schema file** for a wiki... the instructions that the LLM follows when writing and maintaining the wiki are in `AGENTS.md`. This split keeps the human-facing contract clean while giving the LLM a detailed, corpus-specific guide.

`Project Vision/02` §7.1 lists what `AGENTS.md` must contain: purpose and scope, folder structure, page types, naming conventions, citation rules, content rules, special instructions, workflows, and lint/quality rules. None of this is produced or consumed by the current code.

### 2.6 No Structural Change Approval Flow

`Project Vision/01` §7.2 and `Project Vision/07` §5 describe a hybrid approval process:

> The approval process is **hybrid**: simple structural changes (e.g., adding a single folder) are presented interactively in the CLI; complex changes (e.g., reorganizing the entire wiki) are written to a proposal file in `.kimi-code/proposals/` for the user to review and edit later. (`Project Vision/07` §5.1)

Current `detectStructuralProposals` in `src/orchestrator/ingest.ts` only returns an array of proposals; there is no approval gate, no `.kimi-code/proposals/` folder, and no re-ingestion of earlier chunks after acceptance.

### 2.7 Missing or Incomplete Validation Layer

`Project Vision/07` §2 defines the validation order: Critic → deterministic completeness check → deterministic structural checks → schema validation. Today:

- Critic is deterministic schema validation, not LLM review.
- Completeness check (compare LLM-written pages against extracted input) is not implemented.
- Link/citation/schema checks exist in `src/lint/index.ts` but are not integrated as blocking reprocessing triggers.

### 2.8 Index Contract Hierarchy is Partial

`Project Vision/03` describes the contract hierarchy: `index-of-indexes.md` → wiki-level `index.md` → folder-level `index.md`. Current code writes wiki-level `index.md` and folder-level `index.md` contracts, but the folder-level contracts are minimal and do not include page-type catalogs, naming conventions, or folder-specific rules. The `index-of-indexes.md` is written but cross-wiki name surfacing is stubby.

## 3. Guiding Principles for Implementation

The following principles from `Project Vision/01` §3 must remain non-negotiable across every sprint:

1. **The LLM Writes All Markdown Content.** Deterministic code extracts, validates, and orchestrates; it never drafts or mutates markdown bodies.
2. **Citation-Backed Knowledge.** Every factual claim uses `[^srcN]` mapped to a `sources` entry in the frontmatter.
3. **Compounding, Not Ephemeral.** Each `ingest` run enriches existing pages and creates new ones; nothing is lost.
4. **Human Approval for Structural Changes.** New folders or reorganization require human approval; new page types inside existing folders do not.
5. **Context-Cautious Chunking.** Chunks are page-based; never split inside a page, table, or figure.

## 5. Sprint 1: Foundation — `init`, Workspace Scaffolding, and Status Gate

### 5.1 Why This Sprint First

`Project Vision/04` §2 states that before the orchestrator runs, `init` must:

> create the workspace and wiki folders; create an empty `raw/` folder for the PDFs; write a skeleton `AGENTS.md` file with the user's high-level description of the wiki; create a skeleton wiki-level `index.md`.

Without `init`, the user cannot express the wiki's purpose up front, and `AGENTS.md` cannot exist as a schema/system prompt for later steps.

### 5.2 Scope

- Implement `init <slug>` command in `src/cli.ts` and `src/commands/init.ts`.
- Create the workspace directory structure:
  ```
  wikis/<slug>/
  ├── raw/
  ├── config.json
  ├── index.md
  ├── AGENTS.md
  └── chunking-strategy.md (empty or stub)
  ```
- `init` must be interactive or accept CLI flags for title and description:
  - `llm-wiki-cli init donations --title "Political Donations" --description "Annual filings..."`
  - If flags are missing, prompt for title and description.
- Write a skeleton `AGENTS.md` containing:
  - Purpose and scope (from user input).
  - Placeholder folder structure section.
  - Placeholder page types section.
  - Citation and content rules (default boilerplate from `Project Vision/02` §7.1).
  - Workflows section reminding the LLM to update contracts.
- Write a skeleton wiki-level `index.md` with `type: index`, scope, and empty children list.
- Set wiki status to `"initialized"` (not `"ready"` — `sample` moves it to `"ready"`).
- Update `status` command to show initialized/sampled/ready states.

### 5.3 Technical Acceptance Criteria (TAC)

1. `npm run build` succeeds with no TypeScript errors.
2. `npm run test` passes; new tests cover:
   - `init` creates the expected folder tree.
   - Missing required flags prompt the user (tested with mocked stdin).
   - Skeleton `AGENTS.md` contains all sections listed in `Project Vision/02` §7.1.
   - `init` fails if the wiki already exists unless `--force` is passed.
3. `AGENTS.md` and `index.md` are valid YAML frontmatter + markdown.
4. Wiki status is persisted in `config.json` as `"initialized"`.

### 5.4 User Acceptance Criteria (UAT)

1. Running `llm-wiki-cli init donations` creates `wikis/donations/` with an empty `raw/`, a `config.json`, a skeleton `AGENTS.md`, and a skeleton `index.md`.
2. The user can open `AGENTS.md` and see a purpose section that matches what they typed.
3. Running `llm-wiki-cli ingest donations` before `sample` warns: "Wiki is not ready; run sample first."
4. The generated `AGENTS.md` is a valid markdown file with YAML frontmatter.

## 6. Sprint 2: Extraction & Chunking — From PDFs to Page-Based Chunks

### 6.1 Why This Sprint

`Project Vision/01` §3 Principle 5 says:

> PDFs are processed in chunks sized to fit within the configured LLM context limit. Chunks are **page-based**: a chunk is one or more consecutive pages, and the system never splits inside a page, table, or figure. The system errs on the side of more, smaller chunks to leave ample context for the LLM's planning and writing prompts.

`Project Vision/01` §8.3 adds:

> `ingest` is incremental. It tracks every PDF by SHA-256 hash... New PDFs are processed in full. Changed PDFs are re-processed... Unchanged PDFs are skipped.

Extraction and chunking are the deterministic prerequisites for every LLM step. They must be solid before the LLM is asked to write anything.

### 6.2 Scope

- Refine `src/extractor/pdf.ts` to:
  - Use `pdfjs-dist/legacy/build/pdf.mjs` with `useSystemFonts: true`.
  - Read the whole file into memory as `Uint8Array`.
  - Extract text, detect tables, detect figures, and flag scanned pages.
  - Preserve `physicalPage` and `logicalPage` numbers.
  - Record extraction warnings.
- Refine `src/chunking/chunker.ts` to:
  - Group consecutive pages into chunks based on configured token/context limit.
  - Never split a page, table, or figure across chunks.
  - Prefer smaller chunks over larger ones.
  - Mark boundary type (`page`, `table`, `figure`, `heading`).
- Ensure `src/chunking/analyzer.ts` produces a structure summary with headings, sections, and reading-order flags.
- Ensure `src/ingestion/state.ts` tracks:
  - Per-source SHA-256.
  - Per-source derived pages (document, raw, source).
  - Per-source entity/topic counts.
  - Rolling memory reference.
- Implement incremental diff logic: added/changed/removed detection.
- Preserve scanned pages as `raw` pages.

### 6.3 TAC

1. `npm run test` passes with new tests for:
   - A 10-page PDF is chunked into page-based chunks (no page split).
   - A PDF with a multi-page table keeps the table in a single chunk.
   - A scanned-only page is flagged `isScanned` and a raw page is produced later.
   - Re-running `ingest` with an unchanged PDF skips it (SHA-256 match).
   - Changing one byte in a PDF causes re-processing.
   - Removing a PDF causes its derived pages to be removed.
2. Extraction produces `ExtractionResult` with `pages`, `tables`, `figures`, `warnings`, `physicalPages`, `logicalPages`, and `sha256`.
3. Chunking strategy document is written to `chunking-strategy.md`.

### 6.4 UAT

1. Placing `annual-report.pdf` in `wikis/acme/raw/` and running `ingest` produces chunks named `documents/annual-report-part-001.md`, etc.
2. The chunking strategy file explains why each chunk boundary was chosen.
3. Re-running `ingest` immediately after the first run reports "0 sources changed" and finishes quickly.
4. A PDF with a scanned page produces a `raw/annual-report-page-005.md` page with a note that it is image-only.

## 7. Sprint 3: Deterministic Provenance Layer

### 7.1 Why This Sprint

Before the LLM writes anything, the system must be able to produce the **provenance anchors** that every citation will rely on. `Project Vision/06` §4 says:

> Every source PDF has a corresponding `source` page. The `source` page is the provenance anchor for all citations to that PDF.

`Project Vision/05` §5 specifies the `source` page frontmatter: `file`, `sha256`, `pages`, `ingested`, `warnings`. §4 specifies `document` pages as containers for raw material. §6 specifies `raw` pages for unparseable fragments.

### 7.2 Scope

- Implement `src/writers/source.ts` to write deterministic `source` pages with:
  - File path and SHA-256.
  - Page count and metadata.
  - Warnings (e.g., scanned pages).
  - Links to derived document and raw pages.
- Implement `src/writers/raw.ts` to write deterministic `raw` pages with:
  - Source PDF and page number.
  - Reason (scanned/image-only).
  - Any OCR text or image metadata.
- Implement baseline `src/writers/document.ts` to write deterministic document pages that contain:
  - Frontmatter with `title`, `type: document`, `wiki`, `sources` (file + page range), `tags`, `confidence`.
  - Extracted text organized by headings.
  - Tables preserved as markdown tables.
  - Figure descriptions.
  - No LLM synthesis yet — this is the fallback when the LLM fails (per `Project Vision/07` §7 Error Handling and Recovery).
- Implement `src/writers/index.ts` to write wiki-level `index.md` and `index-of-indexes.md` with counts and links.

### 7.3 TAC

1. Every source PDF produces a `sources/<slug>.md` with valid frontmatter matching `Project Vision/05` §5.
2. Every scanned page produces a `raw/<source>-page-<NNN>.md` with valid frontmatter matching `Project Vision/05` §8.
3. Every chunk produces a `documents/<source>-part-<NNN>.md` with valid frontmatter and extracted text.
4. Tests verify that the source page SHA-256 matches the file on disk.
5. Tests verify that all citations in a document page map to a `sources` entry with a valid file and page range.

### 7.4 UAT

1. After `ingest`, `output/sources/` contains one page per PDF with a SHA-256 hash.
2. Opening a document page shows the extracted text, tables, and figure descriptions from the chunk.
3. A scanned page is represented in `output/raw/` with a note explaining it could not be parsed.
4. The wiki-level `index.md` lists the number of sources, document pages, and raw pages.

## 8. Sprint 4: LLM as Author — `AGENTS.md` and ChunkWriter

### 8.1 Why This Sprint

This is the pivotal sprint. `Project Vision/01` §3 Principle 1 says the LLM must write all markdown. The two mechanisms that enable this are:

1. A **per-wiki `AGENTS.md` ingestion guide** that the LLM reads before writing (`Project Vision/02` §7, §8).
2. A **ChunkWriter** that calls the LLM to produce markdown bodies with synthesis, citations, and wikilinks (`Project Vision/04` §4.4.6).

### 8.2 Scope

#### 8.2.1 `AGENTS.md` Generation During `sample`

During `sample`, after the corpus has been analyzed, the LLM must produce a full `AGENTS.md` for the wiki. The content must follow `Project Vision/02` §7.1:

- Purpose and scope.
- Folder structure (discovered from the corpus).
- Page types (default + any new types discovered).
- Naming conventions.
- Citation rules.
- Content rules.
- Special instructions (corpus-specific).
- Workflows (how to handle `sample`, `ingest`, maintenance).
- Lint / quality rules.

`Project Vision/02` §7.2 emphasizes:

> When the LLM ingests a new PDF, it should read the current `AGENTS.md` first. The document acts as the LLM's memory of the project's conventions.

Implementation:
- Add a new writer `src/writers/agents.ts` that takes the folder plan, page types, and naming conventions and writes `wikis/<slug>/AGENTS.md`.
- Update `src/orchestrator/index.ts` (`runSampleOrchestrator`) to:
  - Read the skeleton `AGENTS.md` from `init`.
  - Pass it to a new LLM prompt that produces the full `AGENTS.md`.
  - Write the full `AGENTS.md` to disk after human review (optional — can be auto-approved for `AGENTS.md` content).
- Update `src/orchestrator/ingest.ts` (`runIngestOrchestrator`) to read the current `AGENTS.md` at the start of each source/chunk and pass it to the LLM context.

#### 8.2.2 LLM-Driven ChunkWriter

`Project Vision/04` §4.4.6 describes ChunkWriter:

> Receives the page plan and all extracted material. Writes the markdown body of each page, including: LLM-written synthesis and summaries; faithful transcription of extracted text, tables, and figures; inline citations (`[^srcN]`); wikilinks to related pages. Updates existing pages by appending new evidence and mentions without losing existing detail. Updates the `index.md` contracts to include new pages and page types.

Implementation:
- Rewrite `chunkWriter` in `src/orchestrator/agents.ts` to call the LLM with a structured prompt containing:
  - The current `AGENTS.md`.
  - The rolling memory summary.
  - The page plan from PagePlanner.
  - The extracted text, tables, and figures for the chunk.
  - Existing page content (if updating).
- The LLM response must be parsed into a set of page updates. Each update contains:
  - `filePath`
  - `frontmatter` (YAML)
  - `body` (markdown with `[^srcN]` and `[[...]]`)
- The ChunkWriter must handle both new pages and updates to existing pages, preserving existing detail.

#### 8.2.3 Document Page Synthesis

Update `src/writers/document.ts` to accept LLM-written content. The deterministic fallback remains available for when the LLM fails.

### 8.3 TAC

1. After `sample`, `wikis/<slug>/AGENTS.md` contains all sections listed in `Project Vision/02` §7.1.
2. `AGENTS.md` is re-read at the start of every `ingest` chunk and passed to the LLM context.
3. `ChunkWriter` produces pages with:
   - LLM-written synthesis at the top.
   - Preserved extracted detail below.
   - Inline `[^srcN]` citations for every factual claim.
   - `[[Page Name]]` wikilinks to related entity/topic/document pages.
4. Tests verify that document pages contain at least one `[^srcN]` citation and at least one `[[...]]` wikilink when the corpus contains entities.
5. Tests verify that updating an existing page does not overwrite earlier content.
6. `npm run build` and `npm run test` pass.

### 8.4 UAT

1. Running `sample` on a corpus produces a `wikis/<slug>/AGENTS.md` that describes the folder structure, page types, and citation rules for this specific corpus.
2. Running `ingest` on the same corpus produces document pages that begin with an LLM-written summary, not just raw extracted text.
3. The summary contains inline citations like `[^src1]` that map to a `sources` entry in the frontmatter.
4. Entity names in the summary are linked like `[[Acme Corp]]`.
5. The full extracted text is still preserved below the summary.

## 9. Sprint 5: LLM Sub-Agent Pipeline

### 9.1 Why This Sprint

`Project Vision/04` §1 and §4.4 define the seven sub-agents. Currently, only `PagePlanner` calls the LLM (and shallowly). The other agents are deterministic stubs. For the vision to hold, each agent must be an LLM-driven role that consumes the outputs of the previous agents and the rolling memory.

### 9.2 Scope

Convert each sub-agent in `src/orchestrator/agents.ts` to an LLM-driven function (or an LLM-driven wrapper with deterministic fallback):

1. **StructureAnalyst** — LLM prompt receives the chunk text and metadata; returns headings, sections, tables, figures, page boundaries, and reading-order flags. Fallback to current heuristic if the LLM is unavailable.
2. **EntityExtractor** — LLM prompt receives the chunk and current entity list from rolling memory; returns a list of named entities with types, normalized names, and mention locations. Must be far more accurate than regex.
3. **RelationshipExtractor** — LLM prompt receives entities and chunk text; returns explicit relationships ("X is CEO of Y") and co-occurrence relationships with evidence and page ranges.
4. **EvidenceCollector** — LLM prompt receives chunk text and entities; returns specific claims, numbers, dates, quotes, and their source locations.
5. **PagePlanner** — LLM prompt receives all previous outputs, `AGENTS.md`, and rolling memory; returns a page plan with new pages, updates, folder placements, and structural proposals if needed.
6. **ChunkWriter** — Already LLM-driven from Sprint 4; this sprint focuses on integration with the other agents' outputs.
7. **Critic** — LLM prompt receives the drafted pages, page plan, extracted input, and `AGENTS.md`; returns approval or blocking issues with suggested fixes. (This is a separate agent from the deterministic validation that follows.)

All agents must share a consistent prompt context:
- Current `AGENTS.md`.
- Rolling memory (compressed summary + structured state).
- Source PDF metadata.
- Current chunk text and structure.

### 9.3 TAC

1. Each sub-agent has a dedicated prompt builder and LLM response parser in `src/orchestrator/agents.ts`.
2. Each sub-agent has a deterministic fallback when the LLM is disabled or returns invalid JSON.
3. The orchestrator pipeline (`src/orchestrator/index.ts` and `ingest.ts`) runs the seven agents in order and passes outputs forward.
4. LLM calls are logged in the run log (no raw PDF bytes, only extracted text and metadata).
5. Tests verify that each agent returns a valid structured output when given a sample chunk.
6. Tests verify that the pipeline can process a chunk end-to-end without crashing when the LLM is in `test` mode.

### 9.4 UAT

1. Running `ingest` on a corpus with named people and companies produces entity pages for the most significant ones.
2. Entity pages contain a description, relationships, and a list of mentions with citations.
3. Topic pages are created for recurring themes.
4. Document pages mention related entities and topics and link to them.
5. The run log shows multiple LLM calls (one per sub-agent) for each processed chunk.

## 10. Sprint 6: Dynamic Structure & Human Approval

### 10.1 Why This Sprint

`Project Vision/01` §8.2 says the `sample` command must adapt to the document category. `Project Vision/03` §4 says the folder structure is discovered during `sample` and `ingest`, not fixed in advance. `Project Vision/01` §3 Principle 4 and `Project Vision/07` §5 require human approval for structural changes.

### 10.2 Scope

#### 10.2.1 Sampling Strategies

Implement the four strategies from `Project Vision/01` §8.2:

- **Single very large document:** Look for TOC in first 50 pages; if found, use it; if not, perform a full read during sample.
- **Collection of similar, manageable-sized documents:** Read one document fully, then sample pages from remaining documents.
- **Collection of similar but very large documents:** Read the first document fully to create the strategy; process the rest with `ingest`.
- **Mixed corpus:** Classify each document and apply the appropriate strategy per group.

Implementation:
- Add `src/orchestrator/sampling.ts` with strategy detection and execution.
- The `sample` command should discover all PDFs in `raw/`, classify them, and apply the right strategy.
- The output is a folder plan and `AGENTS.md` that can accommodate all document types.

#### 10.2.2 Dynamic Folder Planning

- `PagePlanner` must propose folders based on the corpus, not just the default `documents`, `sources`, `entities`, `topics`, `raw`.
- New page types inside existing folders are auto-approved (`Project Vision/01` §3 Principle 4).
- New folders require a structural change proposal.

#### 10.2.3 Structural Change Proposals

`Project Vision/07` §5.1 describes the hybrid approval process:

> Simple structural changes (e.g., adding a single folder) are presented interactively in the CLI. Complex changes (e.g., reorganizing the entire wiki) are written to a proposal file in `.kimi-code/proposals/` for the user to review and edit later.

Implementation:
- Add `src/orchestrator/proposals.ts` to:
  - Detect when a proposed folder structure differs from the current one.
  - Classify the change as simple or complex.
  - For simple changes: prompt the user interactively in the CLI (`Approve? y/n`).
  - For complex changes: write a proposal file to `.kimi-code/proposals/<timestamp>-structural-change.md` with reason, affected pages, proposed structure, pros/cons, and required contract updates.
- Add a command or flag to apply approved proposals: `llm-wiki-cli apply-proposal <slug> <proposal-file>` or auto-apply on next `sample`/`ingest` if the proposal file is marked approved.
- If a proposal is rejected, fall back to the existing structure.
- After accepting a proposal that affects existing pages, re-ingest earlier chunks to align them with the new structure.

### 10.3 TAC

1. `sample` discovers all PDFs in `raw/` and classifies the corpus into one of the four strategies.
2. Each strategy produces a folder plan and `AGENTS.md`.
3. The proposal system writes `.kimi-code/proposals/` files for complex structural changes.
4. Interactive approval works for simple changes (tested with mocked stdin).
5. Rejected proposals leave the existing structure unchanged.
6. Accepted proposals trigger re-ingestion of affected earlier chunks.
7. Tests cover all four sampling strategies with fixture PDFs.

### 10.4 UAT

1. Placing one 2,000-page PDF in `raw/` and running `sample` triggers the "single very large document" strategy and searches for a TOC in the first 50 pages.
2. Placing 15 annual reports in `raw/` and running `sample` triggers the "similar, manageable-sized documents" strategy and reads one fully plus a subset of others.
3. Running `ingest` on a corpus that needs a new folder (`timeline/` for chronological events) pauses and asks the user to approve the new folder.
4. After approving, the new folder appears with a folder-level `index.md` contract, and earlier pages are reorganized if needed.
5. The user can review complex proposals in `.kimi-code/proposals/` before deciding.

## 11. Sprint 7: Validation, Quality & Cross-Wiki

### 11.1 Why This Sprint

`Project Vision/07` §2 defines the validation order: Critic → completeness check → structural checks → schema validation. `Project Vision/01` §2.1 requires a top-level `index-of-indexes.md`. `Project Vision/03` §3 requires the cascading `index.md` contract hierarchy. This sprint hardens the system and makes it usable across multiple wikis.

### 11.2 Scope

#### 11.2.1 LLM Critic Agent

`Project Vision/07` §2.1:

> The **Critic** is the seventh sub-agent in the orchestrator pipeline. It reviews the LLM-written pages and the page plan for: quality and clarity of writing; completeness; consistency; correctness; adherence to `AGENTS.md`.

Implementation:
- Add a true LLM Critic in `src/orchestrator/agents.ts` that receives the drafted pages, the page plan, the extracted input, `AGENTS.md`, and rolling memory.
- It returns `approved` or `blocked` with a list of issues and suggested fixes.
- If blocked, the pipeline reprocesses the chunk with feedback.
- Max reprocessing attempts configurable (default 3).

#### 11.2.2 Deterministic Completeness Check

`Project Vision/07` §2.2:

> After the Critic approves, the local deterministic layer compares the LLM-written pages against the extracted input to ensure that: no text was dropped; tables were preserved verbatim; figures were described; no material was materially altered.

Implementation:
- Add `src/validation/completeness.ts` with functions that:
  - Check that every paragraph in the extracted text appears in the markdown body (allowing for reordering and rephrasing, but not omission).
  - Check that every table cell is preserved.
  - Check that figures are described.
- This check runs after the Critic and before structural/schema checks.
- If it fails, the chunk is reprocessed with feedback.

#### 11.2.3 Structural & Schema Checks

- Broken wikilink detection: every `[[Page Name]]` must point to an existing file.
- Citation integrity: every `[^srcN]` must map to a `sources` entry; the source file must exist in `raw/`.
- Orphaned page detection: pages should have incoming links unless they are `index` or `source` pages.
- Duplicate entity flagging: very similar entity names are flagged for merging.
- Schema validation: required frontmatter fields per page type (`Project Vision/05`).

#### 11.2.4 Lint Report

`Project Vision/07` §4:

> After each ingestion run, the system writes a lint report to the wiki's output folder, typically `output/lint/report.json`. The report contains: total page count and pages by type; number of errors and warnings; broken links; orphaned pages; citation integrity issues; duplicate entity flags; stale pages.

Implementation:
- Enhance `src/lint/index.ts` to produce the report structure described above.
- Write `output/lint/report.json` after every `ingest` run.

#### 11.2.5 Error Handling and Recovery

`Project Vision/07` §7:

> If a chunk fails validation repeatedly, the system has several options: quarantine the chunk; fallback to deterministic extraction; abort the run.

Implementation:
- Configurable recovery mode per wiki (`aggressive`, `fallback`, `abort`).
- Quarantine: write extracted text to a `failed/` or `raw/` page.
- Fallback: write deterministic document page.
- Abort: stop the run and report the error.

#### 11.2.6 Cross-Wiki Index and Name Discovery

`Project Vision/01` §2.1:

> The top-level entry point. It lists every wiki in the workspace, how many sources each one has, and how many pages were generated in total.

`Project Vision/03` §3.1 describes `index-of-indexes.md` listing every wiki, source counts, and page counts.

Implementation:
- Ensure `src/writers/index.ts` writes a valid `index-of-indexes.md`.
- Ensure `src/orchestrator/wiki-of-wiki.ts` surfaces cross-wiki names (entities or topics that appear in multiple wikis).
- The wiki-of-wiki agent should call the LLM only with extracted summaries and entity lists, never with raw PDFs.

### 11.3 TAC

1. The LLM Critic returns `approved` or `blocked` with structured feedback.
2. Completeness check fails if an extracted paragraph is missing from the final markdown.
3. Lint report matches the schema in `Project Vision/07` §4 and is written to `output/lint/report.json`.
4. Broken wikilinks and missing citations are flagged in the lint report.
5. Cross-wiki name discovery produces a list of names appearing in multiple wikis.
6. `index-of-indexes.md` is updated after every `ingest` run in a multi-wiki workspace.
7. Recovery modes (`quarantine`, `fallback`, `abort`) are tested.
8. `npm run build` and `npm run test` pass.

### 11.4 UAT

1. Running `ingest` produces a lint report at `output/lint/report.json` with page counts, errors, and warnings.
2. If a document page is missing a citation, the lint report flags it and the pipeline may reprocess the chunk.
3. In a workspace with multiple wikis, `index-of-indexes.md` lists all wikis and cross-wiki names.
4. If a chunk repeatedly fails, the system writes the extracted text to a `raw/` or `failed/` page instead of crashing.
5. The final wiki has a cascading `index.md` contract hierarchy that a human can navigate without opening every content page.

## 12. Cross-Cutting Concerns

### 12.1 LLM Configuration and Security

`AGENTS.md` states:

- LLM config lives in `.kimi-code/config.json` under the `llm` key.
- Supported providers: `openai`, `anthropic`, `openai-compatible`, `kimi`, `test`.
- Kimi Code uses Anthropic messages format, POST to `{baseUrl}/v1/messages`.
- The LLM only receives extracted text and metadata — **never raw PDF bytes**.

Every sprint must respect these rules. Tests should run in `test` mode by default.

### 12.2 ESM and TypeScript Conventions

`AGENTS.md` states:

- ESM imports must end in `.js` even though source files are `.ts`.
- Strict TypeScript: no implicit `any`.
- Path handling: use `path.join`, `path.resolve`, and `toRelativePath` from `workspace.ts`. Forward slashes in stored relative paths.

These apply to every sprint.

### 12.3 Run Logs

`AGENTS.md` states:

- Every command writes a JSON run log to `.kimi-code/logs/` via `buildRunLog`/`writeRunLog`.
- Run logs never include API keys or raw content.

Each new command and new LLM-driven step must be reflected in run logs.

### 12.4 Testing Strategy

- Use Vitest fixtures in `tests/fixtures/`.
- Include valid/bad workspaces and generated PDFs.
- Keep `npm run test` green after every sprint.
- Tests in `test` mode must not require real API keys.

## 14. Definition of Done for the Whole Project

The project is done when a user can:

1. Run `llm-wiki-cli init <slug>` to create a wiki with a purpose-driven `AGENTS.md`.
2. Copy PDFs into `wikis/<slug>/raw/` and run `sample` to discover the corpus structure.
3. Review the generated `AGENTS.md` and folder-level `index.md` contracts.
4. Run `ingest` to produce a compounding, citation-backed wiki where every factual claim has a `[^srcN]` citation.
5. Add new PDFs later and re-run `ingest`; unchanged PDFs are skipped, existing pages are updated.
6. Approve or reject structural changes that create new folders.
7. Browse `index-of-indexes.md` → wiki-level `index.md` → folder-level `index.md` → content pages.
8. Verify any claim by following the citation back to the source PDF and page range.
9. Open `output/lint/report.json` to see the wiki's health.
