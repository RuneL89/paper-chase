## 1. Executive Summary

This revised plan translates the canonical requirements in `Project Vision/` and `AGENTS.md` into a sequence of nine implementation sprints. The original seven-sprint plan was revised to address four critical weaknesses: an overloaded Sprint 4, a circular dependency between sampling strategy and `AGENTS.md` generation, hand-waved re-ingestion after structural changes, and undefined test-mode/schema-validation infrastructure.

The current codebase has the *scaffolding* of the LLM Wiki CLI (workspace discovery, PDF extraction, chunking, state management, basic writers, and orchestrator stubs) but is **not yet a true LLM-driven wiki compiler**. The biggest gaps remain:

1. The **LLM is not the author of markdown content**.
2. The **sub-agents are regex/heuristic stubs**, not LLM agents.
3. There is **no `init` command** and **no per-wiki `AGENTS.md` ingestion guide** produced during `sample`.
4. **Structural change proposals** and human approval are not implemented.
5. **Sampling strategies** for different document categories are not implemented.
6. The **Critic** is a deterministic schema checker, not an LLM review agent.
7. **Completeness checks** that compare LLM-written pages back to extracted input are missing.

This plan resolves those gaps across nine sprints. Each sprint is independently shippable and ends with both technical acceptance criteria (TAC) and user-acceptance criteria (UAT). Every requirement is tied back to the `Project Vision/` files and `AGENTS.md`.

## 2. Current State Analysis

The current codebase has 39 TypeScript files under `src/`. A quick audit against the vision reveals the following gaps.

### 2.1 Missing `init` Command

`Project Vision/01` §8.1 states:

> A new wiki is created with an `init <slug>` command. This command: creates the workspace directory structure; creates the wiki folder `wikis/<slug>/` with an empty `raw/` folder; writes an initial `AGENTS.md` ingestion guide tailored to the wiki's expected content; creates a skeleton wiki-level `index.md`.

`AGENTS.md` lists the commands as `sample, ingest, ingest-all, status, configure-llm, test-llm` — `init` is missing. Today the user must manually create the wiki folder before running `sample`.

### 2.2 `sample` is Document-Centric, Not Corpus-Centric

The vision says `sample` analyzes the *corpus* in `raw/` and chooses a sampling strategy:

> The sampling strategy must adapt to the nature of the documents in the corpus. The orchestrator chooses or is configured with a strategy appropriate to the document collection, such as: a collection of smaller, similar documents; a single very large document; a collection of similar but very large documents; a mixed corpus. (`Project Vision/01` §8.2)

Current `sample` takes a single `pdfPath` argument and processes that one PDF. It does not classify the corpus, select a strategy, or produce a corpus-level folder plan.

### 2.3 The LLM Does Not Write Markdown Content

`Project Vision/01` §3 Principle 1 is explicit:

> The LLM does all research, planning, and writing of markdown. This includes not only synthesized summaries, analyses, and connections, but also the faithful transcription of extracted text, tables, and figure descriptions into markdown.

Current `src/writers/document.ts` writes a deterministic template containing chunk title, page range, and extracted text. The orchestrator's `chunkWriter` returns only `{ files: Record<fileName, title> }`. There is no LLM-driven synthesis, no key-claims section, and no inline `[^srcN]` citations generated by the LLM.

### 2.4 Sub-Agents Are Deterministic Stubs

`Project Vision/04` §4.4 describes the seven sub-agents as LLM-driven roles. Current implementations are deterministic stubs. Only `PagePlanner` calls the LLM, and shallowly.

### 2.5 No Per-Wiki `AGENTS.md` Ingestion Guide

`Project Vision/02` §7 says:

> `AGENTS.md` is the **schema file** for a wiki... the instructions that the LLM follows when writing and maintaining the wiki are in `AGENTS.md`.

`Project Vision/02` §7.1 lists what `AGENTS.md` must contain: purpose and scope, folder structure, page types, naming conventions, citation rules, content rules, special instructions, workflows, and lint/quality rules. None of this is produced or consumed by the current code.

### 2.6 No Structural Change Approval Flow

`Project Vision/01` §7.2 and `Project Vision/07` §5 describe a hybrid approval process. Current `detectStructuralProposals` only returns an array of proposals; there is no approval gate, no `.kimi-code/proposals/` folder, and no re-ingestion of earlier chunks after acceptance.

### 2.7 Missing or Incomplete Validation Layer

`Project Vision/07` §2 defines the validation order: Critic → completeness check → structural checks → schema validation. Today the Critic is deterministic schema validation, not LLM review, and completeness checks are not implemented.

### 2.8 `ingest-all` and `chunking-strategy.md` Authorship Are Undefined

The `ingest-all` command exists in the current codebase but is not explicitly scoped. `chunking-strategy.md` is written but its authorship (LLM vs deterministic) and format are not specified.

### 2.9 `ingestion/engine.ts` is Overloaded

`ingestion/engine.ts` is 22,571 characters while the content writers are much smaller. The engine contains content-generation logic that should move into the writers or the orchestrator when the ChunkWriter becomes LLM-driven.

## 3. Guiding Principles for Implementation

The following principles from `Project Vision/01` §3 must remain non-negotiable across every sprint:

1. **The LLM Writes All Markdown Content.** Deterministic code extracts, validates, and orchestrates; it never drafts or mutates markdown bodies.
2. **Citation-Backed Knowledge.** Every factual claim uses `[^srcN]` mapped to a `sources` entry in the frontmatter.
3. **Compounding, Not Ephemeral.** Each `ingest` run enriches existing pages and creates new ones; nothing is lost.
4. **Human Approval for Structural Changes.** New folders or reorganization require human approval; new page types inside existing folders do not.
5. **Context-Cautious Chunking.** Chunks are page-based; never split inside a page, table, or figure.

## 6. Sprint Summaries

Detailed instructions, TAC, UAT, and the TDD methodology for each sprint are in `plan/Plan_implementation/sprint-NN-*/instruction.md`. The summaries below quote the relevant `Project Vision/` sections.

### Sprint 1 — Foundation + Test Infrastructure

`Project Vision/04` §2 states that `init` must create the workspace, an empty `raw/` folder, a skeleton `AGENTS.md`, and a skeleton wiki-level `index.md`. This sprint implements that.

This sprint also resolves two cross-cutting omissions from the original plan:

- **Test mode**: Add a `test` provider in `src/llm/client.ts` that returns canned, deterministic JSON responses for every LLM sub-agent. This allows every subsequent sprint's TAC to be verified without real API keys or network calls.
- **Frontmatter schema validation**: Adopt a runtime validation approach (e.g., Zod or custom TypeScript validators) to verify required YAML frontmatter fields per page type. This is essential because the LLM will generate YAML in later sprints.

### Sprint 2 — Extraction & Chunking

`Project Vision/01` §3 Principle 5 says:

> PDFs are processed in chunks sized to fit within the configured LLM context limit. Chunks are **page-based**: a chunk is one or more consecutive pages, and the system never splits inside a page, table, or figure.

This sprint refines `src/extractor/pdf.ts` and `src/chunking/chunker.ts`, implements SHA-256 incremental state tracking, and clarifies that `chunking-strategy.md` is a **deterministic audit trail** written by the chunking analyzer, not the LLM.

### Sprint 3 — Deterministic Provenance Layer + `ingest-all`

`Project Vision/06` §4 says:

> Every source PDF has a corresponding `source` page. The `source` page is the provenance anchor for all citations to that PDF.

This sprint implements the deterministic source, raw, and document page writers. It also explicitly scopes `ingest-all` to iterate over all wikis and update the top-level `index-of-indexes.md` once.

### Sprint 4a — Sampling Strategies & `AGENTS.md`

`Project Vision/01` §8.2 lists the four sampling strategies:

> A collection of smaller, similar documents; a single very large document; a collection of similar but very large documents; a mixed corpus.

This sprint classifies the corpus, applies the right strategy, and then generates the full per-wiki `AGENTS.md` ingestion guide as specified in `Project Vision/02` §7.1. By placing sampling before `AGENTS.md` generation, we avoid the circular dependency in the original plan.

### Sprint 4b — LLM-Driven ChunkWriter

`Project Vision/04` §4.4.6 describes ChunkWriter:

> Receives the page plan and all extracted material. Writes the markdown body of each page, including: LLM-written synthesis and summaries; faithful transcription of extracted text, tables, and figures; inline citations (`[^srcN]`); wikilinks to related pages.

This sprint also acknowledges the refactoring risk: `ingestion/engine.ts` currently contains content-generation logic that must move into the ChunkWriter/writers. The refactoring is done incrementally while keeping existing tests green.

### Sprint 5 — LLM Sub-Agent Pipeline

`Project Vision/04` §4.4 defines the seven sub-agents. This sprint converts each from a deterministic stub to an LLM-driven role that consumes the current `AGENTS.md`, rolling memory, and previous agents' outputs.

### Sprint 6 — Dynamic Structure & Human Approval

`Project Vision/07` §5.1 describes the hybrid approval process:

> Simple structural changes (e.g., adding a single folder) are presented interactively in the CLI. Complex changes (e.g., reorganizing the entire wiki) are written to a proposal file in `.kimi-code/proposals/` for the user to review and edit later.

This sprint implements the proposal detection, classification, and approval flow.

### Sprint 7 — Selective Re-ingestion

`Project Vision/07` §6 says:

> When `AGENTS.md` or the folder structure changes, earlier chunks may no longer be organized correctly. The system must support **re-ingestion** of earlier chunks so that: every page is placed in the correct folder; every page follows the latest `AGENTS.md` conventions; the `index.md` contracts reflect the new structure.

This sprint defines the selective re-ingestion strategy: identify affected pages by intersecting new rules with existing state, re-process only those pages, and preserve manual user edits unless a page is being reprocessed.

### Sprint 8 — Validation, Quality & Cross-Wiki

`Project Vision/07` §2 defines the validation order: Critic → completeness check → structural checks → schema validation. This sprint implements the LLM Critic, deterministic completeness checks, lint reports, and cross-wiki `index-of-indexes.md` discovery.

### Sprint 9 — README Documentation

Rewrite `README.md` with the required five sections: introduction/elevator pitch, functional architecture, step-by-step app flow, detailed technical architecture, and project structure.

## 7. Cross-Cutting Concerns

### 7.1 LLM Configuration and Security

`AGENTS.md` states:

- LLM config lives in `.kimi-code/config.json` under the `llm` key.
- Supported providers: `openai`, `anthropic`, `openai-compatible`, `kimi`, `test`.
- The LLM only receives extracted text and metadata — **never raw PDF bytes**.

Every sprint must respect these rules. Tests run in `test` mode by default.

### 7.2 ESM and TypeScript Conventions

`AGENTS.md` states:

- ESM imports must end in `.js` even though source files are `.ts`.
- Strict TypeScript: no implicit `any`.
- Path handling: use `path.join`, `path.resolve`, and `toRelativePath` from `workspace.ts`.

These apply to every sprint.

### 7.3 Run Logs

`AGENTS.md` states:

- Every command writes a JSON run log to `.kimi-code/logs/` via `buildRunLog`/`writeRunLog`.

Each new command and new LLM-driven step must be reflected in run logs.

### 7.4 Testing Strategy

- Use Vitest fixtures in `tests/fixtures/`.
- Include valid/bad workspaces and generated PDFs.
- Keep `npm run test` green after every sprint.
- Tests in `test` mode must not require real API keys.

### 7.5 LLM Resilience and Retries

Every sprint that calls the LLM must respect a common resilience layer defined in Sprint 1:

- Exponential backoff with jitter: 1s, 2s, 4s, 8s. Maximum **3 retries** per LLM call.
- Per-provider request queue with configurable concurrency (default **5** parallel requests).
- Respect `Retry-After` headers when present.
- Malformed JSON is retried once with a stricter prompt; if still malformed, the chunk falls back to deterministic output.
- A circuit breaker pauses the run if more than 30% of chunks fail in a 5-minute window.
- Recovery mode is configurable per wiki (`aggressive`, `fallback`, `abort`). Default: `fallback`.

The mid-run resume mechanism (`--resume` flag and per-chunk state files) is implemented in Sprint 4b, but the directory and state schema are defined in Sprint 1.

### 7.6 Rolling Memory and Compaction

`Project Vision/04` §5 describes rolling memory as a compressed natural-language summary plus a structured state object. Sprint 1 defines the format; Sprint 5 implements compaction:

- Natural-language summary: `output/.state/memory-summary.md`.
- Structured state: `output/.state/rolling-memory.json`.
- Summary token cap: **8,000 tokens** by default (configurable).
- Structured state caps: **500 entities, 200 topics, 500 relationships**.
- Compaction trigger: archive the oldest **20%** when a cap is exceeded.
- Overflow behavior: if compaction cannot reduce the summary below the cap, switch to **summary-only mode**.
- Persistence: written to disk after every chunk for resume safety.

### 7.7 Slugification and Disambiguation

Sprint 1 defines and implements the slugification function used by all page writers:

- Unicode **NFKD** normalization → lowercase → replace non-alphanumeric characters with hyphens → collapse consecutive hyphens → trim trailing hyphens.
- Examples: `slugify("Russell Barkley")` → `russell-barkley`; `slugify("Électricité de France")` → `electricite-de-france`.
- Collisions are resolved with an incremental integer suffix: `john-smith.md`, `john-smith-1.md`, `john-smith-2.md`.
- The structured state maps every extracted entity name to its canonical slug so aliases like `"J. Smith"` resolve to `john-smith`.

### 7.8 Authority Matrix

`Project Vision/04` §7 describes the division of authority. This is documented in the developer-facing `AGENTS.md` and enforced in code reviews:

| Role | Authority |
|---|---|
| **User (human)** | High-level purpose, PDF curation, structural approval, when to run commands. |
| **LLM Orchestrator** | Folder structure, page content, entities, links, citations, new page types. |
| **Local deterministic code** | Extraction, hashing, validation, orchestration, file I/O. |
| **Critic** | Whether LLM output is good enough to commit. |

No deterministic code may draft or mutate markdown bodies; no LLM agent may compute hashes or manage file I/O directly.
