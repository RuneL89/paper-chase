## Step 1 — Client: `src/llm/client.ts`

- New exports: `RATE_LIMIT_MAX_ATTEMPTS = 6` and pure `rateLimitStallDelayMs(retry)` → `60_000 * 2^(retry-1)`.
- Retry loop: when the current attempt is a **429 and the caller opted into retries** (`maxRetries > 0`), the per-attempt ceiling becomes 6; otherwise it stays `1 + maxRetries`. `maxRetries: 0` keeps the frozen no-retry default (429 throws on attempt 1, byte-identical today). Non-429 transients stay bounded at 3 attempts with the existing exponential backoff.
- 429 wait = `max(transportRetryDelayMs(attempt), retryAfterSeconds * 1000, rateLimitStallDelayMs(attempt))` — floor applied only at the call site, never inside `transportRetryDelayMs`, so the existing backoff contract and its assertions survive. All waits route through the existing `transportRetrySleeper` seam (no test ever sleeps wall-clock).
- Exhaustion still throws the existing shape — `API error (HTTP 429) after 6 attempt(s): …` — which `isTransientTransportError` already matches.

## Step 2 — TUI stall feedback (your addition)

- `src/llm/client.ts`: new module-level `setRateLimitWaitReporter(fn | null)` (the `setModelRouting`/`setTransportRetrySleeper` precedent). On a 429 retry, a set reporter receives `{ waitSeconds, attempt, maxAttempts }` and owns the 429 message channel (console.warn suppressed); without one, console.warn fires as today, so non-ingest callers are unchanged.
- `src/commands/ingest.ts`: at run start, wire the reporter through `options.onProgress` — line `Rate limited by provider (HTTP 429) — waiting Ns before retry (attempt X/6)...` — and clear it in a `finally` at run end (no cross-run leakage). CLI and TUI both receive it through their existing progress channels.
- `src/tui/ingest-screen.tsx`: no source change needed — the line flows into the existing `progressLines` renderer (ingest-screen.tsx:232/409) and stays visible as the latest line during the wait. Add a screen test that drives a stubbed `ingestFn` emitting the stall line and asserts the frame renders it.
